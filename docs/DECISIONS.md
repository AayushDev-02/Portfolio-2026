# DECISIONS

Append-only. One entry per decision that future-you might otherwise re-litigate.
Never edit or delete an entry — supersede it with a newer one.

---

### 2026-08-28 — Clone fidelity: pixel-perfect first
Build the reference's own layout and copy verbatim in stage 2, then swap in
portfolio content in stage 5. Rationale: separating "does it look right" from
"does it say the right thing" removes the biggest source of half-finished work.
Risk accepted: two passes over the same sections.

### 2026-08-28 — Next.js 15 App Router over Astro/SvelteKit
Astro would be marginally faster for a static page, but the contact system,
i18n routing and a future Three.js layer all favour Next. The reference is also
Next, which makes the clone mechanically closer. Server Components keep the JS
cost near Astro's anyway.

### 2026-08-28 — Tailwind v4, no UI kit
The reference uses Tailwind v4. A component kit (shadcn/MUI) would be fought
rather than used — zero border radius, no shadows, no default look.

### 2026-08-28 — Contact: Resend + Supabase, not Formspree
Submissions are inserted into Postgres *before* the email send, so a Resend
outage or quota exhaustion never loses a message. Costs one extra free-tier
service; buys durability and full control of the form UI.

### 2026-08-28 — No CMS
Bilingual content in typed TS objects with a shared type, so a missing Japanese
key is a compile error. A CMS adds a network hop and a second place for the two
languages to drift apart. Revisit only if project write-ups become long-form.

### 2026-08-28 — Three.js deferred to stage 10, gated on perf budget
`<CanvasSlot>` is built in stage 1 rendering a static poster, so adding 3D later
touches no layout code. If the canvas breaks the stage 7 budget, it does not ship.

### 2026-08-28 — No scroll-jacking
The reference uses natural document scroll. Custom scroll hijacking breaks
mobile momentum, keyboard navigation and accessibility for no visual gain.

### 2026-08-28 — Japanese type: system font stack, not a webfont
`--font-jp` is a system stack (Hiragino Sans → Yu Gothic → Meiryo → Noto Sans JP).
A CJK webfont is 2–8MB even subset, which would blow the stage 7 LCP budget on
the exact audience the site is for. Japanese machines all ship a good gothic face.
Revisit only if the JA page looks visibly wrong on a Windows recruiter's laptop.

### 2026-08-28 — Silkscreen stands in for the reference's pixel face
The reference uses a font called "minecraft", which is not freely licensed.
Silkscreen (Google Fonts, OFL) is the closest open equivalent and is self-hosted
at build time by next/font. It has **no CJK glyphs** — Japanese headings fall
back to `--font-jp`, which is why that stack was decided at stage 1 rather than
stage 4.

### 2026-08-28 — No clsx / tailwind-merge yet
`lib/utils.ts` has a six-line `cn()`. There is no conflicting-utility problem in
this codebase yet, and every dependency is a byte on the critical path. Add
tailwind-merge the first time a real conflict appears, not before.

### 2026-08-28 — CanvasSlot built at stage 1, not stage 10
The Three.js seam is a five-line component that reserves an aspect-ratio box.
Building it now means stage 10 adds a dynamic import and touches no layout code,
and it costs nothing today. It also makes the "no layout depends on the canvas"
rule enforceable rather than aspirational.

### 2026-08-28 — 100dvh, never 100vh
iOS Safari's dynamic toolbar makes `100vh` taller than the visible viewport,
which cuts the footer row off every full-height section. `min-h-dvh` throughout.

### 2026-08-28 — Scaffolded without installing
The environment the project was written in had no npm registry access, so
`pnpm install` has never run and the build has never been verified. The source
is hand-written rather than generated by `create-next-app`. First local
`pnpm install && pnpm dev` is the real stage 0 gate. See SETUP.md.

### 2026-08-29 — Stage 2 content lives in `src/content/reference.ts`, typed and hardcoded
The reference's copy was fetched and transcribed verbatim (fetched 2026-08-29,
see DESIGN-SPEC.md for the source teardown) into one content file, kept
separate from the section components per the project rule that
`components/sections/*` only reads from `content/*`. This makes stage 5's
content swap a matter of replacing this one file's exports, not touching any
section's JSX.

### 2026-08-29 — Two primitives added beyond the original DESIGN-SPEC inventory
`PullQuote` (FEEDBACK's user quotes) and `NumberedItem`/`NumberedList`
(FEEDBACK's plain ranked takeaways, no fill bar) weren't in the stage-1
inventory because the reference's actual FEEDBACK section wasn't inspected in
enough detail at the time. Both follow the existing `CheckItem`/`RankBar`
shape — a `<li>` primitive plus a list wrapper — rather than one-off markup
inside the section component.

### 2026-08-29 — next-intl 4.14.1 added (stage 4)
The one new dependency in stage 4, committed to in PLAN.md §1 from the start.
Chosen over hand-rolled routing because locale detection, the `[locale]`
segment, `hreflang` alternates and server-side message loading are each easy to
get subtly wrong, and next-intl does them without shipping a translation runtime
to the client — messages resolve in RSC, so the client bundle is unchanged.
Rejected: `next-i18next` (Pages-router era), and rolling our own (the
`Accept-Language` negotiation and cookie-override precedence is the fiddly part,
and it is exactly what the library already handles).

### 2026-08-29 — Section content stays typed TS, not next-intl message JSON
next-intl carries UI chrome — the switcher, the skip link, anything that is a
label rather than content. The six sections' actual copy stays in
`src/content/*.ts` behind one shared type, per PLAN.md §2. Two reasons: a
missing Japanese key becomes a compile error rather than a runtime fallback
string, and the content shape is nested and typed (arrays of timeline entries,
ranked results) in a way flat message catalogues model badly. This also keeps
CLAUDE.md rule 2 intact — sections read from `content/*` and nothing else.

### 2026-08-29 — FEEDBACK's five themes rendered as accordion rows
The text-only extraction of the reference site couldn't confirm whether the
five FEEDBACK themes are actually collapsible in the live DOM or just visually
grouped. Rendered as `AccordionRow`s to match PHILOSOPHY's pattern (same
`[+]`/`[-]` disclosure primitive, listed once in DESIGN-SPEC's inventory for
both sections) and because five expanded theme blocks would be a lot of
vertical scroll on mobile either way. Revisit once the reference is visually
compared to this section, not just its text.
